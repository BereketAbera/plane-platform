# SnakeBrawl production release

SnakeBrawl admits up to **100 concurrent guests sitewide**, with at most **25 players per public arena**. Four full arenas can host 100 players. A fifth arena supplies a healthy destination during replacements. The single process also counts spectators and private party guests against the same 100-socket limit. A private party has four seats and each public arena permits at most twelve spectators. The 100-seat single-arena trial closed admission at seven guests. That layout is outside this release.

The exact arena 1.0.5 production image passed two 100-client tests on this VPS using ordinary matchmaking, gameplay and reconnection. The first measured 86.76 seconds of simultaneous full transport occupancy and 22.38 ms worst-room p95 tick work. The independent repeat measured 109.08 seconds of simultaneous full occupancy and 17.24 ms worst-room p95, with one recovered connection and four successful replacements. Growing the largest snakes concurrently still needs a separate host qualification. Six characters, spectating, rematching and parties passed private verification with the production image in two real Chrome browsers. The private browser test observed 954.1 ms p95 input acknowledgment via SSH/Kubernetes port forwarding; a direct public gameplay measurement is separate.

Release 1.1.0 (web and arena, game commit `9917930`) moves snakes on 40-unit grid lanes with four-direction turns and replaces the food with five valued items. Web and arena ship together because the food kinds on the wire changed. Its images passed the image smoke, the release control trial, the TLS proxy smoke and a 100-client local server bench: 25.05 Hz, 7.06 ms p95 tick work and 188 MiB peak RSS. The 100-client VPS trial was not repeated for this release. The 1.0.2 web and 1.0.5 arena images stay imported on the node, and reverting the release pull request restores them.

The arena runs one Guaranteed process with four vCPUs and 2 GiB. The SnakeBrawl quota allows 4400m CPU requests and 2560Mi requested memory. The web requests 200m CPU and 192Mi, with another 200m reserved for its temporary second replica during a rollout. Snapshot writes spread above three players. The production entry point uses a 1200 MiB V8 old-space ceiling, one V8 worker, single-threaded GC and a 32 MiB semispace. Arena metrics stay private. The web keeps the static prelaunch files for rollback. The public route follows the arena readiness check.

The known public hold is main `21df47e209a3c96f61fa82d3610a846b04220a54`, release `cf0aaccb795044b3e8eca9eab15f24080a07b15b`. It serves the prelaunch page and status and runs zero public arena replicas.

## Promotion and recovery

1. Verify the two linux/amd64 image archives, manifest digests and vulnerability scan. Import each into the node's k3s containerd k8s.io namespace and confirm containerd recognizes the **full manifest reference** used by Kubernetes. Keep a verified mode-0600 recovery archive beside the active and previous release on the node. The `docker.io/library/snake-production-*` names identify node-local content; `imagePullPolicy: Never` requires the images to be present before sync. Registry access or GHCR publication is unnecessary for this release.
2. Before adding the Application, plan and apply the hosted Terraform foundation through the established SSH tunnel. Review changes by resource address. The first plan created only the SnakeBrawl namespace, quota and defaults. The second updated the CoreDNS rewrite set and the bootstrap AppProject chart. Retain the existing Terraform state.
3. For a future component change, update its pinned digest in `gitops/clusters/plane-prod/platform/snakebrawl/deployments.yaml` and `policy/hosted-images.txt` together. The `promote-app` workflow accepts `snakebrawl` with component `web` or `arena`. Verify the archive is already imported and its package inventory was produced for this exact digest before merging. A digest on its own does not make an image available on another node.
4. Run `scripts/ci/validate-manifests.sh`, `scripts/ci/check-capacity.sh`, Helm/Kubernetes dry-runs and the browser smoke from the game repo. Merge the reviewed change to main once the private workloads are ready, DNS resolves, and the rollback archive and host health watcher are in place. The existing release CI publishes `deploy/plane-prod`; the Argo root reads that branch. The first release adds the namespace to both Traefik provider lists. This replaces its one hostPort pod; monitor Wayline, Frameflow, Grafana and the other existing hosts until the new pod serves them. Later SnakeBrawl-only changes do not roll Traefik.
5. Roll back this release by reverting its scoped promotion on a normal protected PR. Restore the known hold's arena manifest (zero replicas), game route, policy, and image allowlist. The 4400m quota may stay during rollback; returning it to 4250m is a separate scoped Terraform step after zero replicas are verified. Keep existing release inventories, the mounted prelaunch assets, certificate, DNS records and shared Traefik watch. After CI publishes `deploy/plane-prod`, verify Argo is Synced/Healthy, the arena has zero pods, the apex and party link show prelaunch, and both public reservations and WSS upgrades return 404. The game repo's `node deploy/verify-public.mjs --prelaunch` checks these public gates. The four neighboring cohosts must remain healthy. Recovering content after a node rebuild requires importing the verified OCI archives; namespace recreation would discard the game's telemetry Secrets.

Use the authenticated hosted kubeconfig for `kubectl -n snakebrawl get deployment,pods,events`, `kubectl -n snakebrawl logs deployment/snakebrawl-arena`, `kubectl -n snakebrawl get certificate snakebrawl-tls`, and `kubectl -n argocd get application snakebrawl`. Keep monitoring, metrics and administrative endpoints on the private network.

The hosted scanner re-evaluates the two archived Linux/amd64 package inventories against its current Trivy DB. The verified manifest digest selects the CycloneDX inventory in `policy/node-images/`. The scanner requires the compressed checksum and matching Trivy image config ID and records its inventory provenance. For an upgrade generate a fresh SBOM from the scanned archive, verify its exact OCI manifest/config and platform, and commit the inventory, checksum and pin together. Missing inventories fail the scheduled scan. Keep the full raw archive scan with the game release.

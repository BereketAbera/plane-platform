# Secret rotation

What can be rotated, how, and how to recover from a rotation that stopped partway.

**`make rotate` has run in both environments on 2026-11-05, with the owner's approval, and every evidence line reads PASS**: dev at 07:23Z ([SEC-2-20261105T072331Z.txt](../evidence/runs/SEC-2-20261105T072331Z.txt)), prod-sim at 07:32Z ([SEC-3-BKP-3-20261105T073240Z.txt](../evidence/runs/SEC-3-BKP-3-20261105T073240Z.txt)). In prod-sim a rotation killed with SIGKILL was finished by `RESUME=yes` ([SEC-4-20261105T073843Z.txt](../evidence/runs/SEC-4-20261105T073843Z.txt)), and on the restored cluster another killed the same way was undone by `ROLLBACK=yes` ([SEC-4b-20261105T084615Z.txt](../evidence/runs/SEC-4b-20261105T084615Z.txt)). `SECRET_KEY` did not move in any of these runs.

Preamble for raw commands:

```bash
export PATH="$PWD/.tools/bin:$PATH" KUBECONFIG="$PWD/.local/kubeconfig"
NS=plane-dev
```

## What can be rotated

| Secret | Procedure | Note |
|---|---|---|
| `PG_PASSWORD` (Plane Postgres role) | `make rotate ENV=<env>` | The only scripted rotation |
| `SECRET_KEY` | **Never** | Derives the key for encrypted config rows. `decrypt_data` fails silently to `""`, so nothing errors and configuration just disappears |
| `LIVE_SERVER_SECRET_KEY` | Not worth rotating | In Plane v1.4.3 `live` requires it to be set, and no route uses the check, so a rotation demonstrates nothing |
| `RABBITMQ_PASSWORD` | No script. Separate procedure | The broker's user must change with the value |
| `SILO_ACCESS_KEY`, `SILO_SECRET_KEY` | No script. Separate procedure | Silo root credentials and every consumer must change together |
| Infisical `ENCRYPTION_KEY`, `AUTH_SECRET`, DB password | No procedure | Secret zero, in `.local/secret-zero/`. Losing `ENCRYPTION_KEY` loses all secrets |
| Grafana admin password | Regenerated by the chart | Argo CD ignores the diff on purpose. See `monitoring/README.md` |

**This is scripted rotation with an error window.** Native rotation is a paid Infisical feature. It is not scheduled and it does not give
per-pod credentials. The role is a shared superuser. In-flight Jobs keep the old value. Who read what cannot be shown, because
`auditLogsRetentionDays` is 0 on the free tier.

## Symptoms that bring you here

| Symptom | Meaning |
|---|---|
| A routine rotation is due | Follow the procedure below |
| `make rotate` stopped and printed "Rotation of `<env>` stopped partway" | Infisical, the Secret and the role may disagree |
| "a rotation of `<env>` is already in progress" | A journal exists in `.local/secret-zero/rotation-<env>` |
| Plane pods crash-loop on database auth after someone edited `PG_PASSWORD` in the Infisical UI | The value changed and the role did not |
| `PlanePostgresDown` after a rotation while Postgres is healthy | postgres-exporter still holds the old password. See below |

## Rotate

```bash
make rotate ENV=dev
make rotate ENV=prod-sim CONFIRM=yes
```

What `scripts/rotate.sh` does, checking real state at each step:

1. Preflight. Reads `PG_PASSWORD`, refuses if Infisical, the Secrets and Postgres disagree, and refuses if the API is unhealthy. As a
   negative control, a random password must be rejected over the pod IP.
2. Writes both old and new values to a journal in `.local/secret-zero/rotation-<env>`, mode 0600, before changing anything.
3. Writes the new value to Infisical, and nudges the operator, which otherwise polls every 60 seconds.
4. Waits for `plane-pgdb` and `plane-app-env` to hold the new value, then runs `ALTER ROLE` over the socket.
5. Proves the new password logs in and the old one is rejected, **over the pod IP**. The image trusts the socket and 127.0.0.1, so a
   login there accepts any password and proves nothing.
6. Waits for auto-reload to roll the consumers. If the pod templates are not marked within 120s, restarts them directly.
7. Checks a database-backed API request, that Postgres was not restarted, that `SECRET_KEY` did not move, and that workload generations
   are stable (no self-heal loop).
8. Removes the journal, then takes an Infisical backup, because an older dump holds the old `PG_PASSWORD`. `SKIP_BACKUP=yes` skips it. If it fails,
   the rotation stands and the script exits 3: run `make backup ENV=infisical`.

The window where Plane may fail runs from `ALTER ROLE` until the new api pod is ready. In dev it was about 38 s: of 1002 signed-in readings 38 answered 500, from 07:23:51Z to 07:24:29Z, and 964 answered 200 ([SEC-2-20261105T072331Z-watch.txt](../evidence/runs/SEC-2-20261105T072331Z-watch.txt)). In prod-sim the script's probe printed 39 s, 37 of 60 probes, one unbroken run from 07:32:48Z to 07:33:26Z ([rotate-prod-sim-20261105T073240Z.log](../evidence/runs/rotate-prod-sim-20261105T073240Z.log), [rotate-prod-sim-20261105T073240Z.probe](../evidence/runs/rotate-prod-sim-20261105T073240Z.probe)). No signed-in reading ran beside that one. The rollback below printed 36 s, 12 of 61 probes, with no signed-in reading beside it either. The script measures the window with a probe once a second.

**Read the script's number with care.** In the dev run it printed 60 s, 39 of 62 probes ([rotate-dev-20261105T072345Z.log](../evidence/runs/rotate-dev-20261105T072345Z.log)). The probe is anonymous, and `db_probe` counts anything but its expected 404 as a failure. Plane throttled the same route after 30 requests: the 31st got 429 with `Retry-After` 54 ([SEC-2-throttle-precheck-20261105T061924Z.txt](../evidence/runs/SEC-2-throttle-precheck-20261105T061924Z.txt)). The script's last three failures came 19 s after the signed-in request had recovered, which fits that, though the probe log keeps no status code. A probe left running shows the same shape: from 07:40:17Z to 07:49:55Z the killed prod-sim run's loop read about 30 `ok` then about 28 `fail` in each minute ([rotate-prod-sim-20261105T073843Z.probe](../evidence/runs/rotate-prod-sim-20261105T073843Z.probe)). So measure the window from a signed-in request as well, which is outside the anonymous limit, as [SEC-2-20261105T062211Z-watcher-source.txt](../evidence/runs/SEC-2-20261105T062211Z-watcher-source.txt) does.

## Diagnosis

```bash
ls -la .local/secret-zero/ | grep rotation
ls -1t .local/evidence-raw/rotate-* | head -3
tail -30 "$(ls -1t .local/evidence-raw/rotate-*.log | head -1)"
kubectl -n "$NS" get infisicalstaticsecrets
kubectl -n "$NS" get secret plane-app-env -o jsonpath='{.metadata.annotations.secrets\.infisical\.com/version}{"\n"}'
```

The evidence log holds results and counts, never values, so it may be copied to `docs/evidence/`. Do not print Secret values to your terminal
to compare them. The script reports which side holds which password without showing it.

## Fix

**A rotation that stopped partway.** The script prints what each side holds. Choose one:

```bash
make rotate ENV=dev RESUME=yes     # finish it
make rotate ENV=dev ROLLBACK=yes   # undo it
```

Both run the same steps aimed at a different password, so either is meant to be safe to run twice. The journal is removed only when one succeeds. Prod-sim also
needs `CONFIRM=yes`.

What has run: in prod-sim, a rotation was killed with SIGKILL 4 s in, after `ALTER ROLE`, while it waited for the operator's restart. `RESUME=yes` finished it and exited 0. Postgres took the new password and refused the replaced one, `SECRET_KEY` did not change, and the rollouts finished 33 s after the resume began. The resume ran with `SKIP_BACKUP=yes`, so it took no Infisical backup, and the newest dump held the previous password until `20261105T074912Z` ([SEC-4-20261105T073843Z.txt](../evidence/runs/SEC-4-20261105T073843Z.txt)). So three rotations have finished, two with that backup and this one without.

On the restored cluster, on the same day, another rotation of prod-sim was killed with SIGKILL 4 s in, after `ALTER ROLE`, while it waited for the operator's restart, with `PG_PASSWORD` at version 4. `ROLLBACK=yes` wrote the journal's old password to Infisical as version 5, and the operator synced in 4 s. Postgres took that password and refused the replaced one, the rollouts finished 43 s after the rollback began, Postgres was not restarted, `SECRET_KEY` did not change, and it exited 0. The probe's failures came in two stretches, 08:46:20Z to 08:46:23Z and 08:46:46Z to 08:46:55Z ([SEC-4b-20261105T084615Z.txt](../evidence/runs/SEC-4b-20261105T084615Z.txt), [rotate-prod-sim-20261105T084620Z.log](../evidence/runs/rotate-prod-sim-20261105T084620Z.log), [rotate-prod-sim-20261105T084620Z.probe](../evidence/runs/rotate-prod-sim-20261105T084620Z.probe)). It ran with `SKIP_BACKUP=yes`, so it took no Infisical backup. No independent check compared the password with the one before the rotation, and no smoke run is recorded after it in prod-sim.

Each of those is one stop at one point. A stop between the Infisical write and `ALTER ROLE`: Not tested in Pass 1. Running either one twice: Not tested in Pass 1.

**After a hard stop, check for the probe.** Up to `85bdeb3`, SIGKILL left the script's probe loop running, and it went on spending the anonymous limit once a second. The first killed run's loop was still writing [its probe file](../evidence/runs/rotate-prod-sim-20261105T073843Z.probe) about 15 minutes later: the raw file's last line is at 07:53:32Z, and the copy committed so far reaches 07:48:34Z. The second kill's run stopped its loop by hand ([SEC-4b-20261105T084615Z.txt](../evidence/runs/SEC-4b-20261105T084615Z.txt)). Since `80d38c1` the loop checks that the script is alive, so it should end within a second of a SIGKILL. That has run only on stubs. Make sure no rotation is really running, then stop anything this names:

```bash
pgrep -fl rotate.sh
```

**Someone changed `PG_PASSWORD` by hand in the Infisical UI.** There is no journal to resume, and the script's preflight refuses, because Postgres does not
accept the current Infisical value. Restore the previous value from Infisical's version history, so that Infisical matches the role again, then wait for the
operator to sync and run a normal rotation. Restoring a version in the UI, the Secret following it and the preflight then passing: Not tested in Pass 1.

**postgres-exporter after a rotation.** The exporter reads `plane-pgdb` through environment variables, so at its next reconnection after a rotation `pg_up` could go to 0 and critical `PlanePostgresDown` could fire on a healthy database. It carries `secrets.infisical.com/auto-reload: "true"` (`monitoring/manifests/environments/base/exporters.yaml`). In the dev rotation the operator restarted it by 07:23:49Z, `pg_up` stayed 1 at every 15 s reading, and `PlanePostgresDown` did not fire in dev ([SEC-2-20261105T072331Z-watch.txt](../evidence/runs/SEC-2-20261105T072331Z-watch.txt)). `scripts/rotate.sh` checks and waits for consumers of `plane-app-env` only, so it neither waits for the exporter nor restarts it.

If it still happens, restart it. A rollout restart adds only a template annotation, which Argo CD's three-way diff does not revert:

```bash
kubectl -n "$NS" rollout restart deployment/postgres-exporter
```

**`<no value>` in a Secret.** A template that once rendered with a missing key leaves that literal behind (operator issue #121). The rotate preflight refuses in this state.
Fix the seed, so that all nine keys exist in the Infisical project, using `scripts/infisical-seed.sh`.

## Confirm

```bash
tail -5 "$(ls -1t .local/evidence-raw/rotate-*.log | head -1)"
test ! -d .local/secret-zero/rotation-dev && echo "no journal left"
kubectl -n "$NS" get deploy
make test-e2e ENV=dev
```

You want a final `PASS` line, "Infisical backed up", and no journal. The evidence also records "Postgres rejects the replaced password", "SECRET_KEY unchanged" and "workload generations stable".

In dev every line read PASS and no journal was left. An independent check found the old password refused, the new one accepted and the three Deployments holding the new value ([rotate-dev-20261105T072345Z.log](../evidence/runs/rotate-dev-20261105T072345Z.log), [SEC-2-20261105T072331Z-old-value.txt](../evidence/runs/SEC-2-20261105T072331Z-old-value.txt)). In prod-sim every line read PASS too, by the script's own checks, and no independent check ran beside it ([rotate-prod-sim-20261105T073240Z.log](../evidence/runs/rotate-prod-sim-20261105T073240Z.log)). `make test-e2e` passed afterwards on the rotated password in dev, and in prod-sim after its first rotation ([BKP-2-20261105T074322Z.txt](../evidence/runs/BKP-2-20261105T074322Z.txt), [SEC-3-BKP-3-20261105T073240Z.txt](../evidence/runs/SEC-3-BKP-3-20261105T073240Z.txt)).

`ROLLBACK=yes` returned one interrupted rotation in prod-sim to the journal's old password, by the script's own checks, as [Fix](#fix) describes.

The operator's annotation and Argo CD self-heal did not fight in dev: `plane-dev` stayed Synced, went Progressing and back to Healthy at 07:24:28Z, and the rotation started no sync operation ([SEC-6-20261105T072331Z-application-watch.txt](../evidence/runs/SEC-6-20261105T072331Z-application-watch.txt)). The file runs to 07:40:51Z, and its one operation came at 07:32:41Z, from a replica change made on purpose to test self-heal ([GITOPS-4-20261105T073240Z.txt](../evidence/runs/GITOPS-4-20261105T073240Z.txt)). The api, worker and beat generations did not move again in the watcher's readings to 07:40:17Z ([SEC-2-20261105T072331Z-watch.txt](../evidence/runs/SEC-2-20261105T072331Z-watch.txt)). Prod-sim had no such watch. There the script's 20 s check passed in each run.

Old Plane dumps should stay usable. A backup does not store the database password, a restore authenticates with what the live Secret holds, and `pg_dump` of one database does not include roles, so a restore leaves the role's current password alone. An Infisical dump older than the rotation is different, since it holds the old `PG_PASSWORD`: `make restore ENV=infisical` refuses it in place unless `ALLOW_STALE_PLANE_SECRETS=yes`.
Restoring a Plane backup taken before a rotation: Not tested in Pass 1. Both real Plane restores used dumps taken after that environment's rotation ([BKP-2-20261105T074322Z.txt](../evidence/runs/BKP-2-20261105T074322Z.txt), [SEC-3-BKP-3-20261105T073240Z.txt](../evidence/runs/SEC-3-BKP-3-20261105T073240Z.txt)).

## What not to do

| Do not | Why |
|---|---|
| Rotate or reseed `SECRET_KEY` | Silent loss of encrypted config. `make restore` also compares its fingerprint and refuses a mismatch |
| Change `PG_PASSWORD` in the UI and stop | The role keeps the old value, and Plane fails on its next restart |
| `kubectl edit secret plane-pgdb` | The operator owns it and overwrites it. Infisical is the source |
| Delete the journal to clear an error | It holds the only copy of the other password outside Infisical's version history. Use `RESUME=yes` or `ROLLBACK=yes` |
| Commit or paste anything from `.local/secret-zero/` | Mode 0600 and gitignored for a reason |
| Test the password over `127.0.0.1` | Trust authentication accepts anything there |
| Rotate during a backup | In-flight Jobs keep the old value and can fail at their next connection |

# Technology choices

Every item in the stack, its pinned version, why it is here, what else was considered, and what the choice costs.

**Two platforms run these choices.** Locally, dev and prod-sim share one kind cluster on one laptop. Hosted production, `plane-prod`, is one K3s node on the owner's Contabo VPS, and it reuses nearly every pin below at the same version. [Hosted production](#hosted-production) lists what it adds or replaces, and why. A row above that section describes the local platform unless it says otherwise.

Versions are read from the repository: `tools.lock`, `helm/values/`, `gitops/applications/`, `infrastructure/`, the contract, and for hosted production `gitops/clusters/plane-prod/` and `infrastructure/hosted/plane-prod/`. Where a tool has a digest, the code pins it. This page leaves digests out, so a version bump changes fewer places.

**Limits of this page.** "Alternatives" lists only what research or the code actually weighed. "Research" means the notes written before the build, with the cross-check `CRITIQUE.md` among them. They stayed in the build's working notes and are not committed, so a reader cannot open them, and a statement resting on them alone has no evidence in `docs/evidence/`. Where the project's requirements fixed the tool, it says so, and no comparison was made. Size and memory figures are estimates unless a link to evidence is given. Where a run bears on a choice this page links it, and the test status is in [validation.md](validation.md).

## How versions were chosen

- **Exact pins, no floating tags.** Container images by digest, charts by exact version, CLIs by checksum in `tools.lock`, Terraform providers by version plus `.terraform.lock.hcl`, GitHub Actions by commit SHA.
- **Kubernetes sets the ceiling.** v1.36 is the highest minor that Argo CD 3.5 lists as tested (1.33 to 1.36).
- **No uniform soak rule.** Argo CD 3.6 was rejected for being one or two days old at selection, while kube-prometheus-stack 92.18.0 and Infisical v0.167.6 were taken within a day or so of release. The research cross-check listed this as item C28, which reads "Inconsistent" and says "Pick one rule". Nobody has picked one, and it is a known weakness of these pins.
- **Reading source is not running it.** Most compatibility statements below came from upstream source and chart templates at the pinned tag. Running them on 2026-11-04 corrected several, and [the ADRs](adr/README.md) record those under "What we found when we ran it".

## Footprint

Locally, all of this has to fit in one Docker VM. Research produced an estimate of 5.5 to 9.3 GiB of workload memory idle for two environments. It was derived from a few host measurements, a third-party figure for Plane v1.4.2, and per-workload guesses, and it is not a measurement of this deployment. [Resource utilization](resource-utilization.md#whole-platform) carries the estimates behind that total.

Measured on 2026-11-05 on a quiet cluster, on the final images restored into a new cluster, from Prometheus, in MiB, the idle average and then the top under `make test-load ENV=dev` with no think time: `plane-dev` 1,155 and 1,312; `plane-prod-sim` 1,082 and 1,146; `kube-system` 1,199 and 1,306; `monitoring` 1,018 and 1,062; `infisical` 710 and 735; `argocd` 461 and 562; `traefik` 51 and 56. All pods averaged 5,703 MiB idle and topped out at 6,103. The VM read 8.65 GiB of 13.63 idle and peaked at 9.05 GiB, and that holds the owner's other containers ([windows](evidence/runs/LOAD-3-20261105T092547Z-prometheus-windows.json), [derived](evidence/runs/LOAD-3-20261105T092547Z-derived.txt)).

The limit that bound under that load was CPU, not memory: Postgres's 500 m, with requests flat by 5 virtual users at about 8.9 a second, while the VM never had more than 2.49 of its 12 CPUs busy. That cluster was young, so Prometheus and Loki held little history. On the earlier cluster, with other work on it, the VM peaked at 10.93 GiB at 01:50 UTC ([timeline](evidence/runs/LOAD-3-20261105T074543Z-timeline.json)). This is one laptop with both environments on one node, and it says nothing about a server. [Resource utilization](resource-utilization.md#the-load-window) has the rest, and the earlier run on a busy machine.

Disk was read on the running platform on 2026-11-05 at 02:01 UTC. The kind node's volume held 12.94 GiB by `du`, the four local-service volumes 3.62 GiB, and the node image 1.19 GiB, which makes 17.75 GiB for a first install ([dr-disk-1.txt](evidence/runs/dr-disk-1.txt)). That is a sum of sizes while other work was running, not a before and after of a clean install. The clean install of 2026-11-05 took host free disk from 31 GiB to 19 GiB by `df`, in whole GiB, with the registry, caches and node image already on disk ([summary.txt](evidence/runs/clean-install-20261105T075041Z/summary.txt), [make-status.txt](evidence/runs/clean-install-20261105T075041Z/make-status.txt)). The cold install, with the registry and caches removed first, took it from 31 GiB to 13 GiB, about 18 GiB, and left `Docker.raw` at 40060992 KiB, 38.21 GiB ([summary.txt](evidence/runs/clean-install-20261105T105546Z/summary.txt), [disk-after-install.txt](evidence/runs/clean-install-20261105T105546Z/disk-after-install.txt)). That run built its images twice, because of the umask defect below, and the second build's leftovers were still on disk, so an install with no defect: Not measured in Pass 1. `Docker.raw` around a delete: 38,276,744 KiB and 38,301,404 KiB, at the top and bottom of [the last drill's output](evidence/runs/BKP-6-20261105T130633Z-lose-cluster-make.txt), and they bracket the whole drill, delete and restore, so a delete alone was not read.

The cold install found a gap in how images are built here: nothing checks that an image's own user can read its files. Under umask 077 every file in a build context was 0600, the build kept those modes, and every build step passed. Then web, admin, space and api crashed at start, with Permission denied in the logs of web, admin and api. `b4f6cc9` runs `chmod -R a+rX` on each context ([rebuild](evidence/runs/INST-1-cold-rebuild-20261105T122036Z.txt), [what it looked like](runbooks/clean-rebuild.md#the-umask-defect)). The gates walk an image for brand, leaks and scan findings, and none of them starts it as its own user, so only pods starting showed this.

Hosted production has its own figures, on a node with 47 GiB and 12 vCPU, in [resource-utilization.md](resource-utilization.md#hosted-production). Over the 12 hours to 2026-11-07T19:31Z its pods used 1.6 cores and 4.0 GiB on average, and the node 6.3 GiB of memory, while the quotas held frameflow's share back. That is one VPS with the owner's own small data set, read from Prometheus, and no load test has run there.

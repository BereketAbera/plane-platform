kind cluster. Wayline is not an original product, and most of what these tests exercise is upstream Plane behaviour
running under this platform's configuration.

## Status values

| Status | Meaning |
|---|---|
| PASS | The test ran, met its criterion, and its raw output is in [`docs/evidence/`](evidence/README.md) |
| FAIL | The test ran and the system misbehaved |
| BLOCKED | The test could not run or finish because something it depends on failed or is missing. This says nothing about the system under test |
| NOT RUN | The test was not attempted, or it was attempted and no evidence was captured |

A row changes status only when its evidence is committed. Some rows check more than one thing. Such a row is PASS only
when all of them pass, so a row with one part proven and another not is split in two, or stays NOT RUN and says what did
run.

How script outcomes map to status:

| Script | Outcome | Status |
|---|---|---|
| `tests/e2e/smoke.py` | Exit 0, all named steps PASS. A step reading SKIP does not apply as things stand, and proves nothing either way | PASS |
| `tests/e2e/smoke.py` | Exit 1, at least one FAIL | FAIL |
| `tests/e2e/smoke.py` | Exit 2, no FAIL but a step BLOCKED | BLOCKED |
| `tests/separation/*.py`, `tests/routes/internal-routes.sh` | The same exit codes. A GAP row in the routes test states what it does not close, and is not a failure | The same |
| `scripts/test-netpol.sh` | Any row FAIL | FAIL |
| `scripts/test-netpol.sh` | No FAIL, any row INCONCLUSIVE, which is a DNS failure, no result, or a target that did not answer | BLOCKED, never PASS. Since `01ab74c` this exits 2, and a row that needs something outside the cluster is counted apart and does not make an offline run non-zero |
| `scripts/restore.sh` | A proof step recorded as NOT RUN | Not PASS, even if every other step passed |
| `tests/drills/failed-deploy-rollback.sh`, `failed-migrator.sh`, `pod-restart-persistence.sh`, `clean-restore.sh` | The last line, `RESULT PASS` or `RESULT FAIL` | The same. With `CLEAN_INSTALL_FIRST=yes` that line also counts the clean install's steps, and a failed one of those says nothing about the restore, by the row below. So BKP-6 takes its status from the restore's JSON files and the drill's stages after the install, and BKP-6b from the last line of a run with no install in it |
| `tests/drills/alert-rules.sh` | The last line, `RESULT failures=<n>`, and a `PASS` or `FAIL` line for each rule | PASS at 0. A rule that does not fire is a FAIL about that rule |
| `tests/drills/clean-install.sh` | No `RESULT` line. `summary.txt` in its directory gives each step's exit status and ends with `Steps that failed: N`, and the script exits 0 only when that is 0 | A row takes its status from its own step, so a failed step says nothing about the rows of the others |
| `tests/drills/clean-restore-harness.sh`, `clean-restore-mutants.sh` | `RESULT <n> passed, <n> failed`, and `RESULT <n> caught, <n> survived, <n> did not apply` | No status of their own. Their commands are stubbed, so they show the logic and nothing about the platform, which is how BKP-9 cites them |
| `tests/load/run.sh` | A k6 threshold fails, but the run finished and captured its data | PASS for the measurement. Report the threshold failure in the row, because the thresholds are starting points (`tests/load/plane.js`) |

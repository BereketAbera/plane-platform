# Terraform

Terraform owns the cluster's foundation and hands everything else to Argo CD
([contract section 4](../../docs/platform-contract.md)).

**The kind CLI creates the cluster, not Terraform.** `scripts/cluster-up.sh` does that first. The Kubernetes and Helm
providers read the kubeconfig during plan, and the [provider docs](https://registry.terraform.io/providers/hashicorp/kubernetes/latest/docs)
warn against creating a cluster and its Kubernetes resources in one module.

| Path | Status | Contents |
|---|---|---|
| `modules/foundation` | Used | Namespaces with PSA and platform labels; ResourceQuota and LimitRange per Plane namespace; CoreDNS rewrite |
| `modules/argocd` | Used | Argo CD release; second release with the AppProjects and the root Application |
| `environments/local` | Used | Root module for the kind cluster. State at `.local/terraform/local/terraform.tfstate` |
| `environments/dev`, `environments/prod` | **Untested templates** | Interface documents for pass 2. Nothing to run |

## Workflow

The cluster must be running. From the repo root, with `.tools/bin` on `PATH`:

```bash
TF=infrastructure/terraform/environments/local

mkdir -p .local/terraform/local
terraform fmt -check -recursive infrastructure/terraform
terraform -chdir=$TF init
terraform -chdir=$TF validate
terraform -chdir=$TF plan -out=../../../../.local/terraform/local/plan.tfplan
terraform -chdir=$TF apply ../../../../.local/terraform/local/plan.tfplan
```

`terraform init -backend=false` is enough for `validate`, and needs no cluster. Providers are pinned, and
`.terraform.lock.hcl` carries hashes for `darwin_arm64` and `linux_amd64`. After a provider bump, regenerate both:

```bash
terraform -chdir=$TF providers lock -platform=darwin_arm64 -platform=linux_amd64
```

Admin password, generated by Argo CD at first start and never in Git or state:

```bash
kubectl --context kind-plane-platform -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath='{.data.password}' | base64 -d
```

The UI answers at `http://argocd.localhost/` through Traefik, once the root Application has synced Traefik and the route.
This repo pins no `argocd` CLI, so everything below uses `kubectl` with `KUBECONFIG=.local/kubeconfig`.

## Destroy

```bash
terraform -chdir=$TF destroy
```

Read what this does before running it. For normal teardown use `make destroy`, which deletes the cluster and
this state together.

- **It deletes the namespaces, and with them every PVC and all Plane data.** Run `make backup ENV=all` first.
- **It breaks CoreDNS.** The provider's delete of `kubernetes_config_map_v1_data` removes the `Corefile` key, and
  CoreDNS cannot mount its config at the next restart. Delete the cluster afterwards rather than reusing it.
- It leaves Argo CD's CRDs (`crds.keep`). The root Application has no finalizer, so removing it does not cascade
  through its children.

## Decisions

**AppProjects and the root Application use a second `helm_release`.** `kubernetes_manifest` needs the CRD at plan
time, which fails on an empty cluster. The chart's `extraObjects` fails too, later: the chart ships its CRDs as
ordinary templates, not in `crds/`, and Helm maps every object in a release to an API before it creates any. A
second release installs after the first, so the CRDs exist. It costs one small chart, in `gitops/bootstrap/chart`.

**That chart's content hash is passed as a value.** The Helm provider only sees a local chart's template edits
when `Chart.yaml`'s version changes. The hash makes every edit show up in the plan.

**The Argo CD IngressRoute is not in Helm values or the bootstrap chart.** Traefik's CRD does not exist until Argo CD
has synced Traefik, so Helm would fail with the same "no matches for kind" error. The root Application syncs it from
`gitops/bootstrap/argocd-route` at wave -8, gated by the `traefik` child's health. Until then Argo CD has no route, so
use `kubectl -n argocd port-forward svc/argocd-server 8080:80`.

**Terraform owns the Argo CD release, and Argo CD does not manage itself.** A bad sync cannot take down the controller
that would apply the fix, and `terraform apply` works while Git is down. Argo CD upgrades are therefore not GitOps.

**ResourceQuota sizing** is computed in `modules/foundation/main.tf` from the contract's budget: 2732Mi requests,
7984Mi limits and 24 pods per Plane namespace. That is the steady budget (1424Mi and 4192Mi), plus one surge pod for each
Deployment during a rollout, plus the operator, both exporters, migrator, a backup Job and one ad-hoc pod. It covers
memory and object counts only, since the contract budgets no CPU.

## After a stuck first sync

The root's waves wait for each child to be Healthy, Synced and finished with its own operation (the Lua check in
`helm/values/argocd.yaml`). A `Degraded` child fails the root's sync, and `retry.refresh` makes the next attempt read the
newest commit. A child in any other state, including Healthy but still OutOfSync, holds the root in `Running` with no
retry, so the root will not pick up a new commit until that operation ends.

The root checks a child only when its wave comes round. A crash-looping child that happens to read Healthy at that
moment lets the later waves through, and the root does not go back to look at it again. This happened on the first real
run, when Grafana's sidecars were being killed for memory.

The root's operation message names the child. The child's own status says what it is waiting for:

```bash
export KUBECONFIG=.local/kubeconfig
kubectl --context kind-plane-platform -n argocd get application root \
  -o jsonpath='{.status.operationState.message}{"\n"}'
kubectl --context kind-plane-platform -n argocd get application <child> \
  -o jsonpath='{.status.health.status} {.status.sync.status} {.status.operationState.message}{"\n"}'
```

Fix the cause in Git and publish it. Whether that lands by itself depends on what is waiting:

- A fix to a child's values or manifests reaches the child at its next automated sync or retry. A child waiting on something
  that never turns Degraded, such as a StatefulSet or a Prometheus with no ready pod, gets neither while its operation is open, so
  end that operation. A single-wave chart child has already closed its own, so a new commit starts its automated sync as usual
  (measured on a throwaway stuck Progressing: synced within a second of a hard refresh).
- A fix to a child's Application manifest only reaches the cluster through the root, so end the root's operation.

To end an operation, set its phase. The controller answers within seconds, deletes any running hook, and clears `.operation`:

```bash
kubectl --context kind-plane-platform -n argocd patch application <app> --type merge \
  -p '{"status":{"operationState":{"phase":"Terminating"}}}'
```

Measured on Argo CD v3.5.7, both while a hook ran and during retry backoff: the phase becomes `Failed`, with the message
`Operation terminated`. A terminated operation does not retry, and the same revision does not start again. Automation starts
a new sync only for a newer commit that leaves the Application OutOfSync. A commit that changes only a hook does not: hooks
are not compared, so the Application stays Synced and nothing runs.

## Starting a child ahead of the root's waves

There is no need to end the root's operation. Apply the child's own file from Git, and its automated sync starts at once:

```bash
kubectl --context kind-plane-platform -n argocd apply -f gitops/applications/<child>.yaml
```

Measured with a scratch parent holding on a 60-second hook: the child started immediately. When the parent's wave came, it
adopted the child in place, with the same UID and a tracking annotation added, and finished Synced. Apply the file as it is
at the published commit, because self-heal and the parent's later sync work from Git, not from this copy.

## Pausing automation

Inject failure only after pausing automation on **both** the child and `root`: the root's self-heal reverts a patch to a
child's `syncPolicy`.
